# 遊戲架構轉型計畫

- 文件版本：0.1
- 更新日期：2026-03-14
- 狀態：從現有 demo 架構遷移到遊戲主體架構的草稿骨架
- 文件定位：技術轉型藍圖，負責定義遊戲前端、挑戰核心、橋接層與存檔等技術邊界；產品方向與玩法假設以前置產品文件為準。

## 1. 轉型目標

- 現況：以 Blockly + Python 關卡流程為中心的桌面 demo
- 目標：以劇情驅動的遊戲，程式挑戰成為其中一個子系統
- 轉型原則：可保留的挑戰核心就保留，需要更換的產品外殼就更換

## 1.1 前置依據

- 產品方向、里程碑與未決產品問題：`game_product_direction_plan.md`
- 目前階段需求範圍：`docs/requirements.md`
- 技術選型建議：`game_technology_recommendation.md`

## 2. 現有系統可沿用部分

### 2.1 可直接沿用的核心

- 挑戰資料契約
- 挑戰載入流程
- AST 分析能力
- Judge 規則與測資執行流程
- 基於 WASM 的隔離執行能力

### 2.2 可重構後沿用

- 將 `AppCore` 重構為 `ChallengeEngine` 或等價子系統
- 將 progress abstraction 重構為遊戲存檔整合層
- 將目前 level metadata 調整為挑戰專屬資料模型

### 2.3 高機率需要替換

- 目前以 PySide6 為主的應用程式外殼
- 目前 widget 式的產品主介面
- 目前的進度 UX 流程
- 目前直接嵌入 Blockly 的產品 UI 承載方式

## 3. 目標架構

### 3.1 高層模組

- 遊戲客戶端
- 敘事 / 任務 / 場景系統
- 挑戰整合層
- Block2Python 挑戰核心
- 存檔 / 持久化系統
- 內容製作流程

### 3.2 職責切分

#### 遊戲客戶端

- 世界互動
- 場景轉換
- 對話與過場
- 音視覺呈現
- 存檔 / 讀檔入口
- 劇情場景與編輯頁的切換

#### 挑戰核心

- 載入挑戰規格
- 接收積木 / Python 提交
- 進行程式分析
- 進行程式評測
- 回傳標準化結果

#### 整合層

- 將遊戲事件映射為挑戰開始 / 結束
- 將挑戰結果映射為任務推進
- 保存跨系統狀態
- 協調示範關、支線練習關、工具包與電池能量規則

## 4. 建議的資料模型拆分

- `QuestSpec`：劇情、章節、任務、解鎖、獎勵、分支
- `SceneSpec`：地點、互動點、遭遇與觸發器
- `ChallengeSpec`：題目、程式模式、規則、測資、提示
- `ToolboxSpec`：已解鎖積木、積木群組、工具包使用規則
- `PracticeRunState`：固定 5 題練習關進度、每題是否使用工具包、整組冷卻時間
- `BatteryState`：當前能量百分比、通關門檻、失敗判定
- `SaveGame`：玩家進度、解鎖內容、旗標、挑戰結果

## 5. 遷移策略

### Phase 1. 穩定核心抽離

- 將 challenge engine 從現有 app UI 中抽出
- 定義清楚的 service / API 邊界
- 降低目前 runtime code 對 UI 的直接耦合

### Phase 2. 建立 Vertical Slice 整合

- 將一段故事流程接上一段程式挑戰流程
- 讓成功 / 失敗可以回寫到遊戲進度
- 驗證存檔、重試與回饋循環

### Phase 3. 擴展系統與內容

- 加入更多任務結構
- 建立內容製作流程
- 加入更完整的提示、呈現與平衡調整

## 6. 主要風險

- 遊戲引擎 / 客戶端與目前 Python-first 實作的整合落差
- Blockly 在高品質遊戲 UI 中的整合品質
- 劇情狀態與挑戰狀態共存時的存檔複雜度
- 敘事型章節的內容製作成本
