# 遊戲技術建議書

- 文件版本：0.1
- 更新日期：2026-03-14
- 文件定位：保存目前階段對遊戲技術方向的分析與建議，不代表最終定案

## 1. 目的

本文件用來保存目前對 Block2Python 遊戲化方向的技術分析結果。  
它不是現況描述，也不是最終架構定稿；用途是協助團隊在產品方向逐漸明確時，有一份可討論、可調整的技術建議基準。

## 2. 現況判斷

目前專案的核心優勢在於：

- 既有的 Blockly / Python 關卡能力
- AST 分析與 Judge 機制
- Wasm 執行與基本隔離能力
- 已存在的教學與回饋流程基礎

目前專案的主要限制在於：

- 目前 UI 架構以 PySide6 桌面工具型應用為主
- 現有前端形式較適合作為工具、原型或內部驗證介面
- 若直接把目前 UI 堆成正式遊戲前端，後續在地圖、演出、節點切換、動畫與整體體驗上會很吃力

因此，現有 repo 更適合保留為「程式挑戰核心」，而非直接演化成完整遊戲前端。

## 3. 美術等級建議

### 3.1 建議等級

建議採用：

- 中階、風格明確、可量產的 2D 遊戲美術

這代表：

- 不是 placeholder 級別
- 也不是高成本商業動畫級別
- 而是能支撐劇情演出、節點式主地圖與關卡回饋的獨立遊戲品質

### 3.2 建議的呈現重點

- 節點式主地圖要有清楚辨識度與解鎖回饋
- 角色貼圖與對話框要能支撐劇情互動
- 關卡切換、通關、修復城市、恢復能量等回饋要有基礎演出
- 編程頁面要乾淨、穩定、可讀，不需要過度裝飾

### 3.3 不建議一開始就投入的方向

- 大量逐幀動畫
- 高成本骨架動畫管線
- 大量互動式場景演出
- 高解析長篇過場動畫

理由是目前階段屬於實驗性開發，小規模遊戲階段的目標是驗證玩法與產品方向，而不是先把美術成本推到最高。

## 4. 技術建議

### 4.1 整體建議

建議將技術分成兩層：

- 遊戲前端層
- 程式挑戰核心層

### 4.2 遊戲前端層建議

建議使用：

- `Godot 4`

原因：

- 非常適合 2D 遊戲
- 適合節點式主地圖、對話框、UI 動畫、場景切換
- 桌面單機的建置成本相對合理
- 更符合目前產品型態：獨立規模、2D、重劇情節點與 UI 流程

### 4.3 不建議作為正式遊戲前端的技術

- `PySide6`

理由：

- 適合工具、管理介面、內部編輯器與技術原型
- 不適合承擔正式遊戲前端的地圖、演出、場景切換與整體遊戲感

### 4.4 程式挑戰核心層建議

建議保留目前 Python repo 作為：

- 題目資料核心
- Blockly / Python 轉換能力
- AST 分析
- Judge / 測資驗證
- Wasm 執行與隔離
- AI 助教相關邏輯

也就是說，這個 repo 最有價值的角色不是「遊戲畫面前端」，而是「遊戲中的程式挑戰子系統」。

## 5. 建議的系統分工

### 5.1 遊戲前端

負責：

- 節點式主地圖
- 劇情對話
- 角色 / 城市 / 場景呈現
- 節點解鎖與演出
- 存檔入口與流程控制

### 5.2 程式挑戰核心

負責：

- 關卡資料
- 積木與 Python 作答流程
- 驗證與評測
- 回饋資訊
- 工具包規則
- 電池能量規則

### 5.3 前後層之間的橋接

建議做一層 `challenge bridge` 或等價整合層。

橋接層的責任：

- 從遊戲前端接收目前節點 / 關卡資訊
- 將玩家提交的積木或 Python 傳入挑戰核心
- 接收驗證結果、能量結果、通關結果
- 回寫到遊戲進度與地圖節點狀態

## 6. 美術與內容工具建議

### 6.1 建議工具

- `Aseprite`
  - 適合像素風角色、小型 UI 元件、簡單動畫
- `Krita` 或 `Photoshop`
  - 適合背景、立繪、對話框素材
- `Figma`
  - 適合 UI 流程規劃與介面草稿

### 6.2 暫不建議優先投入的工具

- 高成本專業動畫管線
- 複雜音訊 middleware

原因：

- 現階段仍是玩法與產品方向驗證期
- 先確保流程完整，比先堆高製作成本更重要

## 7. 為什麼是這套建議

這份建議的核心理由不是「哪個技術最流行」，而是「哪個技術最符合目前產品型態與專案現況」。

目前產品方向是：

- 2D
- 電腦單機
- 節點式主地圖
- 對話框式劇情互動
- 進入獨立編程頁面完成關卡

在這個前提下：

- 若繼續用目前 PySide6 UI 當正式前端，會很難做出足夠的遊戲體驗
- 若完全拋棄現有 Python 核心，則會浪費已建立的 Blockly / Judge / Analysis 能力

因此最合理的折衷不是全砍重來，而是：

- 用更適合遊戲的前端承載遊戲
- 保留現有 repo 作為程式挑戰核心

## 8. 建議結論

目前最建議的技術方向是：

- 遊戲前端：`Godot 4`
- 關卡與驗證核心：延續目前 Python repo
- 美術等級：中階、風格明確、可量產的 2D 獨立遊戲品質

這樣的方向最符合目前產品需求，也最能保留現有專案的可用價值。

## 9. 後續待定項目

- 是否正式採用 Godot 4
- 編程頁是嵌入式、外掛式，或獨立場景切換
- 視覺風格是像素、向量，還是手繪 2D
- UI 與主地圖的具體互動方式
- 存檔資料由哪一層主責
