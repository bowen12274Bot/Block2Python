# MVP 下一階段開發計畫大綱

- 文件版本：0.2
- 建立日期：2026-03-06
- 依據文件：
  - 需求：`docs/requirements.md`
  - 技術引入進度驗證書：`docs/development_plans/technical_introduction_plan_verification.md`

## 0. 目的

本文件用於整理「技術引入期完成後，下一階段應優先推進的開發方向」。

上一階段已完成的重點是：建立最小可展示的端到端骨架，包含 UI 殼、Blockly Web 嵌入、AST 基礎檢查、StubJudge、關卡解鎖與本地進度保存。下一階段不再以「先把技術接上」為目標，而是以 **對齊 MVP 需求、補齊可展示學習流程、收斂未決策項目** 為主。

## 1. 現況分析摘要

### 1.1 已具備能力

- 關卡載入、基本 UI 流程、關卡解鎖與進度保存已存在
- Blockly → Python → Analysis → Judge → Feedback 的最小資料流已打通
- AST 分析、Judge、AI 均已有可替換介面，後續可逐步替換真實實作

### 1.2 目前主要缺口

- 需求文件中的多項 MVP 功能仍停留在占位或 stub 階段
- 真實執行/判題機制尚未落地，驗證結果仍主要依賴 StubJudge
- Blockly 內容尚未完整對齊需求範圍（I/O、變數、if/else、for range 等）
- 目前建立期流程中，Blockly 產生的 Python 會直接回填 editor，這與「學生完成積木後再自行撰寫 Python」的產品方向不一致
- 教學頁、劇情/任務入口、趣味互動模式仍未形成明確方案
- 產品體驗仍偏「功能原型」，尚未進入接近遊戲的流程與 UI 設計
- 長鏈劇情、章節推進、關卡路線等遊戲化結構尚未納入資料與流程設計
- AI 助教的邊界、資料來源、提示策略尚未進入規劃細節
- agent skills 的雙重用途尚未被正式規劃：一是開發工具，二是 AI 助教的教學規範來源

## 2. 下一階段核心目標

- 將目前的展示骨架推進為「可對齊需求文件的 MVP Demo」
- 優先完成會直接影響展示內容與學習流程的功能
- 先收斂必要決策，再分拆各主題計畫進入規劃與實作

## 3. 下一階段需要決策的事項

### 3.1 驗證與執行策略

- Python 執行環境選型：本機 subprocess、受限執行器、或其他替代方案
- 超時策略：是否沿用需求草案中的 2000ms，是否允許關卡級覆寫
- 輸出比對策略：換行、尾端空白、錯誤訊息顯示方式
- 是否在 MVP 階段導入真實多測資執行，或先保留部分 stub / 半真實模式
- 是否支援帳號系統，或 Demo 階段維持純本機進度
- 是否納入巢狀結構與作用域概念

### 3.2 Blockly 教學範圍與表示方式

- MVP 階段要支援到哪些積木：是否完整涵蓋 I/O、變數、運算、if/else、for range
- 是否需要自訂 blocks，或先以現成 Blockly blocks + 限制策略完成
- Blockly 關卡限制要如何資料驅動（允許/禁止 blocks、概念對齊）
- Blockly 轉 Python 功能在 MVP 中的定位：是完全不開放、作為提示/對照功能，還是作為學生手動觸發的輔助工具
- 若保留 Blockly 轉 Python，是否禁止自動回填 editor，改為預覽、提示或對照模式

### 3.3 關卡與內容呈現策略

- 教學頁（FR-2）在 Demo 階段的呈現形式：純文字、Markdown、分段卡片、或簡單互動式內容
- 劇情／任務入口（FR-3）要做到什麼程度：僅文字入口、章節結構、還是包含前後事件節點
- 關卡資料是否需要擴充 schema，以承載教學內容、劇情節點、提示策略與互動模式設定

### 3.4 遊戲化流程與 UI 策略

- Demo 要做到何種程度的遊戲感：僅章節包裝，或包含長鏈劇情、路線選擇、節點式推進
- 關卡是否允許分支路線，若允許，解鎖與進度資料要如何表示
- UI 是否需要獨立的世界觀/章節/任務入口畫面，而不是只有實作區
- 視覺風格是否先定一版設計方向，避免後續功能完成但整體體驗仍像工程原型

### 3.5 趣味互動模式策略

- FR-6 要採用哪一種互動模式作為 MVP 示範
- 該互動模式是否共用現有驗證資料流，或需單獨設計轉換層
- 互動模式與一般 Python/Blockly 關卡的切換與解鎖邏輯如何統一

### 3.6 AI 助教邊界與 agent skills 策略

- AI 在 Demo 中是否啟用；若啟用，採 feature flag、手動開關或固定展示模式
- AI 可讀取哪些上下文：學生程式碼、關卡內容、Analysis/Judge 結果、教學內容
- AI 的拒答與防洩題策略要到什麼程度
- agent skills 是否分成「開發用」與「教學用」兩組
- 教學用 skill 與教學頁內容如何分工：哪些內容寫在頁面，哪些內容寫在 skill
- skill 如何與關卡範圍、提示策略、可回答邊界對齊

## 4. 下一階段待規劃的主題

以下項目建議各自拆成獨立計畫文件，而不是直接在本文件中展開細節。

### 4.1 關卡資料結構與內容規劃

- 關卡 schema 是否要擴充以承載：
  - 教學頁內容
  - 劇情／任務入口資料
  - Blockly 限制與概念範圍
  - 驗證規則與提示策略
- 關卡解鎖、劇情進度、教學內容之間的資料關係

### 4.2 真實 Judge / Execution 計畫

- 執行器選型
- 多測資執行流程
- timeout / error / normalization 行為定義
- UI 如何呈現測資失敗與執行錯誤

### 4.3 Blockly 擴充計畫

- MVP 必要積木集合
- toolbox 設計與分類
- generator 與 block JSON/schema 演進策略
- 關卡對應的 blocks 限制與驗證
- Blockly 輸出與 Python 編輯區的關係：哪些資料只做驗證，哪些資料可作為學生參考，但不應直接取代學生撰寫

### 4.4 教學頁與劇情呈現計畫

- 教學頁資料來源與呈現方式
- 劇情／任務入口的最小流程
- 教學內容、任務目標、AI 提示間的對應方式

### 4.5 遊戲化流程與 UI 計畫

- 長鏈劇情與章節結構
- 關卡路線與解鎖表示方式
- UI 風格方向與核心畫面清單
- 世界觀/任務入口/實作區之間的切換流程

### 4.6 趣味互動模式計畫

- 選定互動模式
- 與現有驗證系統的整合方式
- 與關卡流程、提示策略的整合方式

### 4.7 AI 助教與 agent skills 計畫

- 提示政策（hint policy）
- 上下文組裝規格
- 模型回覆邊界與安全策略
- Demo 場控與除錯資訊保留方式
- 教學頁與 skill 的內容分工
- 開發用 skills 與教學用 skills 的管理方式

## 5. 下一階段待實作的主軸

### 5.1 以需求為導向補齊 Blockly

- 將 Blockly 支援範圍補到 MVP 必含教學內容
- 將 Blockly 轉 Python 從建立期主流程調整為可選輔助能力，不取代學生自行撰寫 Python
- 讓 Blockly 關卡限制不再只靠硬編碼或建立期 stub

### 5.2 將 Judge 從 stub 推進到可用版本

- 實作真實程式執行
- 支援多測資與輸出正規化
- 回填 `stderr`、`elapsed_ms`、`exit_code` 等可觀測資訊

### 5.3 擴充 Analysis 以支援教學回饋

- 補足 `for range` 等結構規則
- 改善結構違規訊息的可解釋性
- 為後續 Blockly ↔ Python 對照與 AI 提示預留可讀摘要

### 5.4 補齊關卡展示流程

- 將教學頁與劇情／任務入口從占位提升到可展示版本
- 讓關卡開始、積木挑戰、Python 驗證、通關回饋形成較完整體驗
- 明確區分「積木完成」與「Python 自行作答」兩個階段，避免學生直接沿用 Blockly 生成結果完成 Python 任務

### 5.5 補齊遊戲化包裝與核心 UI

- 增加章節感、任務感或世界觀入口
- 讓主畫面不只是一個實作區
- 補足能支撐 Demo 展示的整體風格與畫面切換

### 5.6 補一種趣味互動模式

- 選定至少一種非自由輸入模式
- 接上既有驗證流程
- 確認其能對應學習目標而不只是展示效果

### 5.7 建立 AI 助教的 skill-based 內容基礎

- 定義教學頁內容與 teaching skills 的分工
- 讓 AI 回覆可依 skill 穩定落在當前關卡範圍
- 預留後續把 skills 作為教案知識來源的資料流

## 6. 下一階段待完善的部分

### 6.1 UI 與回饋呈現

- 測資失敗資訊的可讀性
- Analysis/Judge 回饋區分與摘要
- Blockly 與 Python 頁面的切換體驗
- 主畫面是否具備章節/任務/故事導向的辨識度

### 6.2 內容與資料一致性

- 教學內容、劇情、關卡規則、AI 提示的概念範圍是否一致
- 關卡是否完整對齊需求文件中的 MVP 教學內容
- 教學頁與 teaching skills 是否表達同一套規範與邊界
- 文件、UI 與資料流是否一致反映「Blockly 是前置練習；Python 任務需由學生自行完成」這一原則

### 6.3 觀測與除錯

- Demo 階段至少需要哪些 log/debug 資訊
- 發生錯誤時如何快速定位是 Blockly、Analysis、Judge、還是資料設定問題

### 6.4 驗證與測試

- 除既有 smoke test 外，是否為 Judge、Analysis、levels loader 補最小自動化測試
- 後續是否導入更正式的測試框架與測試資料管理方式

## 7. 建議的推進順序

1. 先決策：Judge 選型、Blockly MVP 範圍、遊戲化呈現程度、教學/劇情最小策略、agent skills 使用邊界
2. 先規劃：拆出 Judge、Blockly、教學/劇情、遊戲化 UI、AI/skills、互動模式等個別計畫文件
3. 先實作主流程：Blockly 範圍補齊、真實 Judge、Analysis 擴充、關卡展示流程、基本遊戲化入口
4. 再完善體驗：UI 回饋、資料一致性、teaching skills 對齊、最小測試與觀測能力
