# 開發專案計畫（Demo 版本）

- 文件版本：0.2
- 更新日期：2026-03-06
- 專案定位：以 Demo 展示為主，不以正式部署/軟體釋出為目標
- 系統端點：僅學生端（不做教師後台）

## 目標族群：國中生

- 約 13–16 歲
- 具備積木式程式設計基礎，準備轉向文字型程式（Python）

## 一、核心目標：積木與 Python 轉換學習平台

- 讓學生理解「積木邏輯結構 ↔ Python 語法結構」的對應
- 以關卡式流程引導完成：積木任務 → Python 任務 → 驗證 → 解鎖下一關
- 以任務/劇情包裝學習流程，整體體驗接近遊戲而非單純工具
- 支援較長鏈的劇情串接、章節推進與可能的關卡路線設計
- UI 不只服務實作區，也需承載世界觀、章節感、任務入口與整體風格

## 二、動機與痛點

1. 積木模式容易操作，但容易停留在「拼出結果」，缺乏對文字語言語法/結構的理解。
2. 學生對學習沒有方向：不知道下一步要學什麼，也不知道如何從積木過渡到 Python。

## 三、目的

1. 引領具備積木知識的學生學會 Python 基礎語法，取得積木與程式之間轉換的思維。

## 四、方法

1. 設計教案（教學頁方案保留可替換空間，呈現形式/結構由組員後續決定）
2. 設計接近遊戲的學習體驗
   - 以章節、任務、劇情節點與可能的關卡路線來包裝學習流程
   - UI 需有一致風格，而非只呈現編輯器與提交區
   - 劇情與教學需能串接，但避免互相綁死
3. AI 輔助教學教案（方向性）
   - 可讀取學生程式碼用於診斷與提示
   - 不直接提供完整解答；不引入超出當前關卡範圍的概念
   - 模型邊界與教案橋接屬待設計項，Demo 先以可控為優先
4. agent skills 技術導入（雙用途）
   - 作為本系統開發工具：協助團隊與 AI 進行更高效且一致的開發
   - 作為 AI 助教的教學規範來源：讓 AI 在學生提問時，能依據 skill 穩定回覆
   - 後續教學內容可分為「教學頁」與「skill 類型內容」兩部分
   - 教學頁負責課程呈現；skill 負責 AI 提示、規範與回答邊界
5. 階段式學習 Python 語法（以關卡推進）
   1) 讓學生先用積木完成邏輯（建立思路）
   2) 再將同一目標轉成 Python（理解語法表徵）
6. 通過驗證後前往下一關（順序解鎖；後續可擴充路線分支）

## 五、成果呈現

- 可操作 Demo：至少可完整走完一段關卡流程（含積木 → Python → 驗證 → 解鎖）
- 可展示的遊戲化包裝：至少包含任務入口、劇情串場或章節感 UI
- 展示素材：流程圖/架構圖 + 螢幕錄影或截圖（依團隊需要）

## 六、成果分析

- 小規模測試（同學/目標年齡相近者）：完成率、卡關點、常見錯誤
- 回饋蒐集：是否理解積木與 Python 對應、是否覺得學習更有方向、劇情是否提升投入感

## 七、結論

- 以 Demo 為主先驗證「積木 → Python」轉換式學習流程的可行性與吸引力，再決定後續擴充（內容深度、劇情設計、AI 方案等）。

### 風險提醒（劇情 vs 教學設計）

- 風險：為提升學生興趣而加入劇情，可能反過來限制教學設計；若劇情先定稿但教學範圍/關卡設計後續變更，將導致大量返工（「劇情改教學」或「教學遷就劇情」都會成本很高）。
- 建議作法（Demo 階段）：
  - 先鎖定教學範圍與關卡學習目標（至少 MVP 範圍與關卡順序），再進行劇情細稿。
  - 劇情與教學解耦：以「章節/任務殼 + 可替換文本」為主，避免把關鍵教學步驟寫死在不可改的劇情流程中。
  - 劇情先做「可抽換/可刪減」：Demo 優先用短對話/旁白串場，不做過度複雜的分支選擇。

### 風險提醒（agent skills 雙重用途）

- 風險：若開發用 skills 與教學用 skills 混在一起管理，後續容易產生用途混淆、內容污染與維護困難。
- 建議作法（Demo 階段）：
  - 明確區分「開發用 skills」與「AI 助教用 skills」兩個範疇。
  - 開發用 skills 服務團隊協作效率；教學用 skills 服務學生互動穩定性。
  - 教學用 skills 應與教學頁、關卡範圍、提示策略一起設計，避免 skill 內容超出當前關卡概念。
